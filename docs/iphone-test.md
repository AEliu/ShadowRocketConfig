# 三组 iPhone 验收（尚未执行）

先保存旧配置，导入新离线版，选择有效节点和“配置”路由，停用覆盖规则/DNS 的模块。记录 iOS/Shadowrocket 版本、节点协议、配置 SHA、网络及隧道的本地排除设置。以下预期均需手机验证，电脑测试不能代替。

## 1. 导入、分流与 IPv6/LAN

- 确认没有编译错误，记录从导入到可连接的耗时。检查导出配置仍保留 `IP-CIDR6` 和 `always-real-ip`。
- 实际打开百度、B 站、App Store，以及 GitHub/Google。查看日志：前者 DIRECT、后者 PROXY；国内访问不应比旧配置明显变差。
- 在规则测试中检查 `2400:3200::1` → DIRECT、`2606:4700:4700::1111` → PROXY。规则测试只能证明匹配，若当前网络支持公网 IPv6，再确认实际 IPv6 请求日志和出口。
- 打开真实 NAS/路由器 IP 和一个实际存在的 `.local` 设备；如要验证 `always-real-ip` 的单播行为，在 hosts.conf 配置真实 `nas.home.arpa` 地址，重建导入，在 App DNS 工具中查询并确认真实私网地址、访问成功。不要拿未配置的内网域名测试。

若远程版也要使用，额外确认五个规则集预览非空。任一解析字段消失、IPv6 错分或 LAN 失效，保留导出文件和日志，恢复旧配置。

## 2. 节点失效、冷启动和 DNS 主备

- 清除可清除的 DNS 缓存并重连，使用未缓存的域名/可控随机子域。先选失效节点：国内站点应仍可用，国外站点应失败。恢复有效节点并重连，国外访问应恢复。
- 在可控 Wi-Fi 路由器上临时阻断主 DNS `223.5.5.5:443`，查一个未缓存的国内域名；日志应显示 DNSPod DoH 备用可用。恢复网络规则。两家都不可达时应报告失败，不应主动退回明文业务 DNS。
- 同时抓取手机 IPv4/IPv6 的 UDP/TCP 53、853 和 DNS 端点 443。普通代理业务域名不应以明文发给本地 DNS；单独记录 `doh.pub` 的冷启动引导查询。国内 DoH 和节点域名解析是预期路径；TXT/SRV 等客户端查询可能交国内解析器。HTTPS 内容无法仅凭抓包读取，需结合 DNS/连接日志。

没有可控路由器或足够日志时，阻断与泄漏项写“未验证”，不能用一个 DNS 泄漏网页代替。不要把 VPN 整体断开后的直连当作配置的节点故障回退。

## 3. 网络恢复与日常稳定性

有效节点下切换 Wi-Fi ↔ 蜂窝、锁屏数分钟再恢复，重复一个国内站点、一个国外站点及常用消息/语音 App。确认无需反复强退才能恢复，且无隧道反复退出。若日常网络是 IPv6-only/NAT64，这一组必须在该网络执行，尤其检查 IP 形式主 DoH 的启动。

若有明显耗时、编译失败或内存退出，记录旧/新配置的同机对照结果；此时再评估更小规则集，不按规则数推断故障原因。失败时切回保存的旧配置即可，无需先改动规则快照。
